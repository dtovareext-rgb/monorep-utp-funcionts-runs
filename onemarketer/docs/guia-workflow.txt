  gcloud workflows run onemarketer-daily-pipeline \
    --project=prd-utpbi-data-operation \
    --location=us-central1 \
    --data='{
      "process_date": "2026-08-10",
      "etl_function_url": "ETL_URL",
      "skip_etl": true,
      "invoke_downstream_sps": true
    }'

Notas:
  - process_date = día de los chats/medios (no “hoy” del job).
  - Sin process_date: el Workflow usa AYER America/Lima (UTC-5). Scheduler 4 AM del 14 → procesa el 13.
  - Timeout HTTP del ETL en el Workflow: 1800 s. Si la CF tarda >30 min,
    el Workflow puede cortar aunque la CF siga; en ese caso usar skip_etl
    o revisar el tope de medios (candidato a Fase 2 Job paralelo).
  - Timeout SPs (STT / Gemini) en el conector BQ: 14400 s (4 h).

6) SCHEDULER → WORKFLOW (reemplaza Scheduler → CF directa)
================================================================================

Crear (o actualizar) Scheduler apuntando al Workflow, NO a la CF:

  gcloud scheduler jobs create http onemarketer-daily-pipeline-sched \
    --project=prd-utpbi-data-operation \
    --location=us-central1 \
    --schedule="0 4 * * *" \
    --time-zone="America/Lima" \
    --uri="https://workflowexecutions.googleapis.com/v1/projects/prd-utpbi-data-operation/locations/us-central1/workflows/onemarketer-daily-pipeline/executions" \
    --http-method=POST \
    --oauth-service-account-email=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com \
    --message-body='{
      "argument": "{\"etl_function_url\":\"ETL_URL\",\"invoke_downstream_sps\":true}"
    }' \
    --headers="Content-Type=application/json"

Si ya existe un Scheduler solo a la CF (scheduler-setup.sh), desactívalo o
bórralo para no duplicar el ETL.

Sin process_date en el body, el Workflow usa “ayer” UTC-5.

8) BACKFILL reporteAtenciones (skill tardío)
================================================================================

reporteAtenciones suele cargar fecha_evento con ~2 días de lag (ej. job del 25
con fecha_evento 23). Gemini no espera esa tabla: inserta el hist y el backfill
pega después por idcase = SAFE_CAST(id_case AS INT64).

Columnas nuevas en hist raw/prd:
  skill, channel, category_description, agent_open, agent_close,
  start_time, end_time, time_wait_operator
  asesor_user  ← reporte_chats.user (último operador/asesor <> robot;
                 si no hay humano, NULL — p.ej. fuera de horario)

Desplegar (una vez ALTER + SP, luego workflow):

  bq query --use_legacy_sql=false --location=US \
    --project_id=prd-utpbi-data-operation \
    --impersonate_service_account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com \
    < onemarketer/bigquery/sqls/alter_hist_caso_atenciones_cols.sql

  bq query --use_legacy_sql=false --location=US \
    --project_id=prd-utpbi-data-operation \
    --impersonate_service_account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com \
    < onemarketer/bigquery/procedures/sp_onemarketer_backfill_atenciones.sql

  gcloud workflows deploy onemarketer-daily-pipeline ...

One-shot (todos los skill NULL, sin ventana 14 días):

  bq query --use_legacy_sql=false --location=US \
    --project_id=prd-utpbi-data-operation \
    --impersonate_service_account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com \
    < onemarketer/bigquery/sqls/backfill_atenciones_skill_nulls_hoy.sql

El SP diario mira process_date − 14 días: actualiza skill NULL (atenciones)
y asesor_user NULL (chats, mismo día). Lo de solo-bot queda asesor_user NULL.

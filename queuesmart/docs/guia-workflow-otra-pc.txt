1) QUÉ CAMBIÓ (resumen)
================================================================================

A) Workflow
   - Timeout del conector del WORKER: 14400 s (4 horas). Antes cortaba a 1800 s.
   - Orquesta: prepare → worker → consolidate → gen_ia → analisis
   - invoke_downstream_sps default = true

B) SPs desacoplados (IMPORTANTE — correr CREATE OR REPLACE en BQ)
   - sp_queuesmart_mp3_consolidate: YA NO hace CALL a gen_ia
   - sp_queuesmart_mp3_gen_ia: YA NO hace CALL a analisis
   - El Workflow llama los 3 en secuencia y valida errores

C) Job (ya en imagen): prepare/worker, pass-through/FLAC, extensión real, etc.


================================================================================
2) ORDEN EN LA OTRA PC
================================================================================

  1. Clonar / copiar monorepo (o subir YAMLs/SQLs a Cloud Shell)
  2. Redeploy SPs en BigQuery (quitar CALL anidados)
  3. Redeploy Cloud Workflow (YAML con timeout 4h + invoke_downstream_sps true)
  4. Probar con gcloud workflows run
  5. (Opcional) Scheduler diario apuntando al Workflow, NO al Job

    --project=prd-utpbi-data-operation \
    --location=us-central1 \
    --source=daily_pipeline.yaml \
    --service-account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com \
    --impersonate-service-account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com

Si el YAML está en el home de Cloud Shell:

  --source=daily_pipeline.yaml

Tras el deploy, la revisión debe subir (000007, 000008, …).


================================================================================
5) CORRER EL WORKFLOW (manual, sin Scheduler)
================================================================================

Ejemplo día completo (ingesta + 3 SPs):

  gcloud workflows run queuesmart-daily-pipeline \
    --project=prd-utpbi-data-operation \
    --location=us-central1 \
    --impersonate-service-account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com \
    --data='{
      "process_date": "2026-06-19",
      "project_id": "prd-utpbi-data-operation",
      "job_name": "prd-utpbi-s3-to-gcs-micro-batch",
      "gcs_bucket": "prd-utp-stg-queuesmart",
      "max_failed_tasks": 0,
      "invoke_downstream_sps": true
    }'

Notas:
  - process_date = fecha de los audios (nombre archivo), no “hoy”.
  - invoke_downstream_sps true → corre consolidate + gen_ia + analisis.
  - Worker puede tardar >30 min; el YAML tiene timeout 14400 s (4 h).
  - Si ya hay muchos archivos en GCS, worker irá más rápido (already_in_gcs).

Ver ejecución:

  gcloud workflows executions list queuesmart-daily-pipeline \
    --project=prd-utpbi-data-operation \
    --location=us-central1 \
    --limit=5 \
    --impersonate-service-account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com

================================================================================
7) FLUJO QUE EJECUTA EL WORKFLOW
================================================================================

  1. Cloud Run Job role=prepare  (1 task) → manifiesto GCS
       gs://prd-utp-stg-queuesmart/state/manifests/{fecha}.jsonl
       gs://prd-utp-stg-queuesmart/state/manifests/{fecha}.meta.json

  2. Lee meta.count

  3. Cloud Run Job role=worker (tasks=count, parallelism del Job)
       timeout conector Workflow: 14400 s

  4. Si failedCount > max_failed_tasks → PARA (no SPs)

  5. CALL sp_queuesmart_mp3_consolidate(fecha)

  6. CALL sp_queuesmart_mp3_gen_ia(fecha)          # STT

  7. CALL sp_queuesmart_audio_analisis_ia(fecha)   # Gemini

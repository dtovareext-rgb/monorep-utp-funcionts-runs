1. Para quién es esto

Si nunca usaste Cloud Shell: es una terminal Linux dentro del navegador (icono >_ arriba a la derecha en console.cloud.google.com). Ahí corres gcloud (Workflows, Jobs) y bq (BigQuery).

Esta guía explica primero el vocabulario, después impersonate (lo más importante) y al final los comandos listos para copiar.

Regla de oro. El código vive en Git. Lo que corre en producción es lo desplegado. Si cambias un SQL en tu PC y no haces bq query … < archivo.sql, el Workflow sigue usando la versión vieja.

3. Impersonate — léelo entero

3.1 El problema que resuelve

Hay dos identidades:

QuiénPara qué sirve
Túdiego@… (tu login de Cloud Shell)Abrir la terminal, leer el repo. Suele no tener permiso para CALL SPs de prod ni para lanzar el Workflow “en nombre del pipeline”.
El robotgenesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.comEs la SA del Workflow, de los Jobs y de los jobs de BigQuery. Tiene jobUser, dataEditor, run.developer, etc.

Si corres gcloud workflows run … sin impersonate, Google intenta hacerlo como tú. Puede fallar por 403, o peor: crear recursos “tuyos” que el Scheduler (que sí usa la SA) no ve igual.

Impersonate = “Google, yo soy Diego, pero ejecuta este comando como genesys-audio-processor”.

Analogía. Tienes la llave de la oficina (Token Creator). No eres el vigilante, pero puedes pedirle al edificio: “abre la puerta como si yo fuera el vigilante”. El edificio anota: Diego pidió actuar como genesys. El trabajo lo hace el vigilante.

3.2 Qué permiso necesitas TÚ

Sobre la SA genesys-audio-processor@… tu usuario necesita:

roles/iam.serviceAccountTokenCreator (crear token de esa SA).

Sin ese rol verás algo como:

PERMISSION_DENIED: Not found; Unable to impersonate Permission 'iam.serviceAccounts.getAccessToken' denied

Eso no se arregla con otro flag: hay que pedir IAM (Token Creator sobre esa SA).

3.3 El warning que vas a ver siempre (es normal)

WARNING: This command is using service account impersonation. All API calls will be executed as [genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com].

Significa: el comando salió bien encaminado. No es un error.

3.4 El flag no se escribe igual en gcloud y en bq

HerramientaFlag (cópialo tal cual)
gcloud--impersonate-service-account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com
bq--impersonate_service_account=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com
Guiones vs guion bajo. gcloud usa guiones (impersonate-service-account). bq usa guion bajo (impersonate_service_account). Si los mezclas, el comando ni siquiera arranca.

Para no escribirlo 20 veces, al empezar la sesión:

export SA=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com export PROJECT=prd-utpbi-data-operation

3.5 Qué impersonate y qué no

Acción¿Impersonate?Por qué
Correr / listar WorkflowSí (gcloud)El Workflow y sus ejecuciones viven como la SA.
Deploy del YAML del WorkflowSíLa SA queda como service-account del workflow.
Desplegar SP / vista / CALLSí (bq)Los jobs de BQ del pipeline los crea esa SA (mismas tablas, mismos labels).
cd, ls, git clone, nanoNoSon comandos de Linux, no hablan con GCP.
gcloud config set projectNo hace falta impersonateSolo elige el proyecto de tu sesión.

3.6 Dos flags que se parecen (no los confundas)

FlagQué hace
--impersonate-service-account=…Tú lanzas el comando como si fueras la SA.
--service-account=… (en workflows deploy)El Workflow, cuando corra solo (Scheduler), usará esa SA. Es la identidad permanente del workflow, no de tu sesión.

En el deploy de QueeSmart van los dos:

gcloud workflows deploy queuesmart-daily-pipeline \ --project=$PROJECT \ --location=us-central1 \ --source=daily_pipeline.yaml \ --service-account=$SA \ --impersonate-service-account=$SA

--service-account = “este workflow es genesys”. --impersonate = “este deploy lo estoy haciendo yo, actuando como genesys”.

4. Abrir Cloud Shell y dejar el repo

  1. Entra a https://console.cloud.google.com y elige el proyecto prd-utpbi-data-operation.
  2. Clic en el icono >_ (Activate Cloud Shell). Espera a que aparezca el prompt usuario@cloudshell:~$.
  3. Primera vez (o si no está el repo):
gcloud config set project prd-utpbi-data-operation # Clonar (ajusta la URL si usas otro remoto) git clone https://github.com/dtovareext-rgb/monorep-utp-funcionts-runs.git cd monorep-utp-funcionts-runs export SA=genesys-audio-processor@prd-utpbi-data-operation.iam.gserviceaccount.com export PROJECT=prd-utpbi-data-operation

Si ya clonaste otro día: cd monorep-utp-funcionts-runs y git pull.

Para subir un archivo suelto desde tu PC: icono de tres puntos del Cloud Shell → Upload.

5. Comandos que más se usan

5.1 Correr QueeSmart un día (Workflow completo)

Ingesta S3 + consolidate + STT + Gemini. Tarda bastante (el 16 tardó ~1 h 40 min hasta Gemini).

gcloud workflows run queuesmart-daily-pipeline \ --project=$PROJECT \ --location=us-central1 \ --impersonate-service-account=$SA \ --data='{ "process_date": "2026-10-16", "project_id": "prd-utpbi-data-operation", "job_name": "prd-utpbi-s3-to-gcs-micro-batch", "gcs_bucket": "prd-utp-stg-queuesmart", "invoke_downstream_sps": true }'

Cambia process_date al día de los audios. Sin fecha, el YAML usa ayer Lima.

5.2 Ver si terminó y el error

gcloud workflows executions list queuesmart-daily-pipeline \ --project=$PROJECT \ --location=us-central1 \ --limit=5 \ --impersonate-service-account=$SA

Para el detalle de una ejecución (pega el ID que salió en list o en el run):

gcloud workflows executions describe ID-DE-LA-EJECUCION \ --workflow=queuesmart-daily-pipeline \ --project=$PROJECT \ --location=us-central1 \ --impersonate-service-account=$SA

5.3 Solo Gemini (si STT del día ya OK)

Si falló call_sp3 con backendError, no relances el workflow. Llama el SP:

bq query --use_legacy_sql=false --location=US \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ "CALL \`prd-utpbi-data-operation.adf_speech_analytics.sp_queuesmart_audio_analisis_ia\`(DATE '2026-10-16', NULL);"

El SP borra el hist de análisis de esa fecha y lo regenera. Las transcripciones no se tocan.

5.4 Desplegar SPs QueeSmart (cuando cambió el SQL en Git)

Location US. Desde la raíz del monorepo:

bq query --use_legacy_sql=false --location=US \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ < queuesmart/bigquery/procedures/sp_queuesmart_mp3_consolidate_A1.sql bq query --use_legacy_sql=false --location=US \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ < queuesmart/bigquery/procedures/sp_queuesmart_mp3_gen_ia_A2.sql bq query --use_legacy_sql=false --location=US \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ < queuesmart/bigquery/procedures/sp_queuesmart_audio_analisis_ia_A2.sql

El < significa “toma el contenido de este archivo y mándalo a BigQuery”. En Cloud Shell es Linux; no uses la barra invertida de Windows.

En BQ los SPs se llaman sin _A1/_A2. Esos sufijos son solo el archivo en Git.

5.5 Desplegar vistas CRM (location us-central1)

bq query --use_legacy_sql=false --location=us-central1 \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ < queuesmart/bigquery/views/v_queuesmart_counter_crm_lead.sql bq query --use_legacy_sql=false --location=us-central1 \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ < onemarketer/bigquery/views/v_onemarketer_caso_crm_lead.sql bq query --use_legacy_sql=false --location=us-central1 \ --project_id=$PROJECT \ --impersonate_service_account=$SA \ < onemarketer/bigquery/views/v_onemarketer_lead_conversaciones.sql
